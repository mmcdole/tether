Tether · build plan

Tether Build Plan

How the app is structured, the decisions that shape the code, and ten phases to build it in order. Each phase ends with something you can install and use. The screens and requirements come from the Tether design page.

Approach

Standard Android, kept small

This follows Google's recommended app architecture: a UI layer of Compose screens and ViewModels, a data layer of repositories that own the app's state, data flowing one way, and Hilt wiring it together. It skips the parts that only pay off on large teams.

Doing

  • Two Gradle modules: app and a pure-Kotlin mud library
  • One Activity, Compose screens, type-safe Navigation
  • One ViewModel per screen, exposing a single StateFlow<UiState>
  • Repositories as the single source of truth, backed by Room and DataStore
  • A @Singleton SessionManager owns the connection, independent of any screen
  • Constructor injection everywhere, dispatchers injected for tests

Not doing

  • Feature modules or a module per layer
  • A use-case class for every action. The real logic (parsing, rules) already lives in mud
  • An interface for every repository. Only where a test needs a fake
  • MVI libraries, event buses, or a custom base ViewModel
  • Separate model classes per layer when one would do. Room entities map to mud models, and screens use those

Rule of thumb: mud knows MUD protocols and rules, data knows where things are stored and owns the live session, service knows Android lifecycle and notifications, ui knows screens. Nothing in data imports from service or ui.

Core types

The shapes everything hangs on

// mud
data class StyledLine(val id: Long, val text: String, val spans: List<StyleSpan>, val isPrompt: Boolean)
sealed interface Scope { data object Global : Scope; data class World(val worldId: Long) : Scope }
data class Trigger(val id: Long, val scope: Scope, val pattern: Pattern, val actions: List<TriggerAction>,
                   val enabled: Boolean, val group: String?, val replyTemplate: String?)
data class Alias(val id: Long, val scope: Scope, val name: String, val expansion: String, val enabled: Boolean)

// app/data
@Entity data class RuleEntity(@PrimaryKey(autoGenerate = true) val id: Long, val worldId: Long?,  // null = all worlds
                          val kind: RuleKind, val pattern: String, val isRegex: Boolean, val body: String, …)

sealed interface SessionState {
  data object Idle : SessionState
  data class Connecting(val world: World) : SessionState
  data class Connected(val world: World, val since: Instant) : SessionState
  data class Reconnecting(val world: World, val attempt: Int) : SessionState
}

@Singleton class SessionManager @Inject constructor(…) {
  val state: StateFlow<SessionState>
  val scrollback: StateFlow<ScrollbackSnapshot>
  fun connect(world: World); fun disconnect(); fun send(input: String); fun setColumns(cols: Int)
}
Decisions

How the tricky parts work

ConcernDecision
Connection lifetimeThe socket lives in SessionManager, scoped to the app process. Screens observe it and never own it. SessionServiceLauncher watches SessionManager.state and starts SessionService when a session becomes active. The service stops itself when the state returns to Idle. The data layer never references the service.
ThreadingOne read coroutine and one write channel per connection on an injected IO dispatcher. Parsing and triggers run off the main thread. The UI gets immutable snapshots.
Foreground serviceforegroundServiceType="specialUse", because dataSync is time-limited on Android 15. Holds a WifiLock while connected. A partial wake lock is behind a setting, off by default.
KeepaliveTCP keepalive on the socket, plus IAC NOP after 60 s of silence.
Text selectionThe output pane is wrapped in SelectionContainer and has no click, long-press, or double-tap handlers of its own. Pinch-to-resize only reacts when two fingers are down and never consumes one-finger events. While a long-press is in progress (observed, not consumed), the pane freezes its snapshot and counts new lines, so the selection doesn't move.
Output renderingA LazyColumn with reverseLayout, keyed by line id, each line pre-built as an AnnotatedString. Scrollback is 5,000 lines by default. It follows new output only when you're at the bottom.
InputBasicTextField with TextFieldState and lineLimits = SingleLine, so it stays one line and scrolls sideways. imeAction = Send, and it keeps focus after sending. Autocorrect off by default. A vertical swipe on the field steps through command history. Horizontal touches are left to the field.
KeyboardadjustResize, edge-to-edge, imePadding() on the session layout. No custom IME, no accessory bar.
Text size and NAWSText size is one DataStore value. Pinch changes it live and saves on release. Columns are measured with a TextMeasurer from the pane width and font size, and are sent via NAWS (debounced) whenever either changes.
Rules resolutionRuleRepository combines the Room flows for global rules and the current world's rules into a compiled RuleSet. SessionManager holds it as a StateFlow, so edits apply on the next line. Triggers match plain text with colors stripped.
NotificationsTwo channels: Session (ongoing, low importance) and Messages (trigger notifications). Messages use MessagingStyle, grouped by the first capture (the sender). Reply uses RemoteInput with setAuthenticationRequired(true), unless the trigger turns it off.
NavigationNavigation Compose with @Serializable routes: Worlds, WorldEdit(id?), Session, Rules(worldId?), Settings.
VersionsKotlin 2.x, Compose BOM, Material 3, Hilt + KSP, Room, DataStore, kotlinx.serialization, all through libs.versions.toml. minSdk 26, target the latest stable SDK.
Testsmud: plain JUnit with byte and text fixtures, most of the test effort. app: in-memory Room DAO tests, ViewModel tests with fakes and Turbine, a few Compose UI tests for the session screen. One manual acceptance check per phase.
Phases

Build order

Each phase depends on the ones before it. The first five make a client he can actually play on. The next three add rules and notifications. The last one is polish.

  1. Project skeleton

    An installable app with the right structure and nothing in it.

    • Gradle setup with version catalog, app + mud modules, Hilt, KSP
    • TetherApplication, MainActivity with edge-to-edge, TetherNavHost with placeholder screens
    • Black theme: Theme.kt, AnsiColors.kt (the 16-color palette), monospace Type.kt
    • Lint and unit-test tasks running in one command

    Done when: the app installs, opens to an empty black Worlds screen, and ./gradlew check passes.

  2. Protocol core

    Bytes from a MUD become colored lines, entirely in mud.

    • TelnetParser: IAC handling, split across reads, prompts via GA/EOR
    • TelnetNegotiator: TTYPE with MTTS, NAWS, EOR, CHARSET (UTF-8, Latin-1 fallback)
    • AnsiParser to StyledLine: 16, 256 and truecolor, bold-as-bright, underline, reverse, reset
    • Fixture tests built from captured real MUD output

    Done when: captured output from his MUDs parses into the expected text and colors in tests.

  3. Worlds

    Save the MUDs and characters to connect to.

    • Room: TetherDatabase, WorldEntity, WorldDao. Exported schema, migrations from day one
    • WorldRepository. LoginSecrets encrypts the auto-login password with an Android Keystore key
    • Worlds screen (list, +, gear) and World edit screen (name, host, port, TLS flag, auto-login lines), opened by long-pressing a world
    WorldsWorld edit

    Done when: worlds can be added, edited and deleted, and they survive a restart.

  4. Live session

    Play a MUD while the app is open.

    • MudConnection, Scrollback, SessionManager with SessionState
    • Session screen: top bar (world, dot, uptime, rules, ⋮), OutputPane, “N new lines ↓” chip
    • CommandInput: one line, scrolls sideways, Send keeps the keyboard open, swipe for history
    • Text selection in the output with Copy and Select all, as described under Decisions
    • Auto-login lines sent after connect. ; splits commands
    Check before moving on: load 5,000 lines of colored output and make sure selection works across several lines while output keeps arriving. If SelectionContainer over LazyColumn misbehaves, switch the output pane to a read-only TextView with setTextIsSelectable(true) inside AndroidView. That gives Android's own selection. The rest of the app stays the same.
    SessionTypingSelect and copy

    Done when: he can play for an hour with the screen on, colors are right, Gboard is untouched, and selecting text works without fighting the app.

  5. Stay connected

    The main requirement: locking the screen doesn't drop the session.

    • SessionService (specialUse) with the ongoing notification: Open, Disconnect
    • SessionServiceLauncher, WifiLock, TCP keepalive + IAC NOP
    • NetworkMonitor + ReconnectPolicy: reconnect with backoff, replay auto-login, dim “reconnected” line
    • First-run prompts for notifications (Android 13+) and battery optimization
    • Worlds screen: connected-world card with Open and Disconnect (tap again to confirm)
    WorldsScreen off

    Done when: connect, lock the phone for 8 hours on Wi-Fi, unlock, still connected, nothing missing. Then switch Wi-Fi off and on during a session and it reconnects by itself.

  6. Display and settings

    Text size, more room for output, and the settings screen.

    • SettingsRepository on DataStore: text size, hide status bar, autocorrect, keep keyboard open, reconnect, Wi-Fi/CPU locks, scrollback size
    • TextSizeGesture: pinch with the size/columns overlay, saved on release
    • Column measurement and NAWS updates on resize, rotation, keyboard open, and text size change
    • Hide status bar via WindowInsetsControllerCompat, swipe down to show briefly
    • Settings screen with a live text preview, opened from the Worlds gear and the session ⋮ menu
    Text sizeSettings

    Done when: pinching changes the size smoothly, the MUD wraps to the new width, and every setting persists.

  7. Rules engine and commands

    Triggers and aliases work, created by typing.

    • mud/rules: Pattern, TriggerEngine, AliasExpander, RuleSet, all with tests
    • mud/command: CommandParser for #alias, #galias, #action, #gaction, #gag, #ggag, #unalias, #unaction, #ungag
    • RuleEntity (nullable worldId), RuleDao, RuleRepository merging global and world flows
    • Wire into SessionManager: aliases on the way out, triggers on the way in. Echo confirmations like #alias k = kill %1
    • Trigger actions: highlight, gag, send, vibrate. Notify is stored now and posted in phase 8
    • Gags: #gag {pattern} (this world), #ggag (all worlds), #ungag. A gagged line never reaches scrollback or the session log, but every other trigger on that line still runs, so a gag can also send or notify

    Done when: #alias k {kill %1} mid-fight works on the next command, and a global and a world trigger both fire on the same line.

  8. Rules screens

    Manage rules without typing.

    • Rules screen: Triggers / Aliases tabs, the world box and the All worlds box, each with +, toggles, group tags, ▾ world switcher
    • RuleEditorSheet: pattern, actions, applies to, Advanced (send, regex, group, priority, reply template)
    • Long-press a rule: Edit, Copy / move, Delete. CopyMoveSheet with multi-world destinations, plus a prompt when an alias name already exists. Logic lives in RuleTransfer
    • Global rules row on the Worlds screen
    Triggers & aliasesNew triggerCopy or move a rule

    Done when: he can copy a rule from one character to two others in a few taps, and the change takes effect without reconnecting.

  9. Trigger notifications and reply

    Know about tells with the screen off, and answer them.

    • Notify action posts to the Messages channel using MessagingStyle, one conversation per sender
    • Reply template (tell %1) builds a RemoteInput action. Triggers without a template only get Open
    • ReplyReceiver sends through SessionManager, queues the reply if reconnecting, and logs [reply] … in the session
    • Unlock required by default, can be turned off per trigger
    Screen off

    Done when: a tell arrives with the phone locked, he replies from the lock screen, and the other player gets it.

  10. Polish and release build

    Close the gaps before calling it v1.

    • MCCP2 compression and TLS connections
    • Session log to a file, and rules export/import as JSON (RuleJson)
    • R8-minified release build, app icon, signing config
    • A full pass over the design page to confirm every screen matches

    Done when: it replaces whatever client he uses today.

Risks

What could go sideways

  • Text selection in Compose lists. This is the biggest unknown, so it's checked in phase 3 with a fallback ready.
  • Phone makers that kill background apps (some Samsung, Xiaomi, OnePlus settings). The battery prompt helps. The 8-hour test in phase 4 should run on his actual phone.
  • Gboard ignoring the no-autocorrect hint. Some versions still suggest words. If so, he can switch it off in Gboard for this app.
  • Slow regex triggers. Java regex has no timeout. Patterns compile on save, invalid ones are rejected in the editor, and lines over 4 KB skip regex triggers.
  • Play Store review. Only matters if it gets published. Sideloading avoids specialUse review.

Not in v1: scripting, several sessions at once, maps, GMCP gauges, and making a trigger from an output line (dropped; long-press in the output is only for selecting text).
