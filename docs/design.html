Android MUD client · design plan for review

Tether

A MUD client for Android that keeps the connection alive with the screen off, lets you add triggers and aliases mid-fight, leaves Gboard alone, and shows full ANSI color as light text on a black background.

Draft 3. Needs sign-off before we build

“Tether” is a working name. Mockups use example MUD output, not a real session.

Changes

  • Disconnect from the Worlds list. The connected world has its own Disconnect button.
  • Global and per-world rules. Each trigger or alias applies to all worlds or to one world. Use a separate world for each character to give it its own rules.
  • One-line input. The text box is always exactly one line tall. Longer commands scroll sideways.
  • Adjustable text size. Pinch the output to resize it. The same setting is also a slider in Settings.
  • More room for output. Thinner top bar, plus an option to hide Android's status bar.
  • Rules screen. This-world and all-worlds rules are in separate boxes.
  • Select and copy output. Long-press the output for normal text selection across lines, with Copy and Select all.
  • Removed: making a trigger from an output line. Long-press in the output is only for selecting text. New triggers come from + on the Rules screen or #action.
  • Copy rules between worlds. Long-press a rule to copy or move it to any worlds, or to all worlds.
  • Lock-screen reply. New section below explains how it works.

Screens

How it looks

Ten screens cover the whole v1 app. The session screen is where you spend almost all your time, so everything else stays out of its way.

The hard part

Staying connected with the screen off

Most MUD clients drop out because the socket belongs to the Activity, the thing on screen. When Android stops or kills that Activity, the connection goes with it. In Tether the screen only displays the connection. Something else owns it.

What keeps it alive

  • The socket and scrollback live in an app-wide SessionRepository. Rotating the phone, switching apps, or locking the screen never touches them.
  • SessionService is a foreground service started on connect and stopped on disconnect. It shows the ongoing notification and keeps the process alive.
  • The service type is specialUse (“persistent telnet connection”). dataSync is time-limited on Android 15, so it would cut out after a few hours.
  • A WifiLock is held while connected. A partial wake lock is optional, off by default, and only for phones that still drop the connection without it.

What recovers it

  • TCP keepalive, plus a telnet IAC NOP every 60 s, stops routers and carriers from timing out an idle socket.
  • A network callback notices Wi-Fi to cell handoffs and reconnects with backoff. Auto-login runs again, and the session screen shows a dim “reconnected” line.
  • A first-run prompt asks to ignore battery optimization, with a link to the phone maker's settings for brands that kill aggressively.
  • Acceptance test: connect, lock the phone for 8 hours on Wi-Fi, unlock, still connected, nothing missing from scrollback.
Notifications

How reply from the lock screen works

It uses Android's standard inline reply, the same one messaging apps use. Nothing about it is MUD-specific except the command it sends.

  1. A trigger has “Notify” turned on. The global %1 tells you: %2 trigger fires on a tell and posts a notification: title “Hagbard tells you”, body “wanna group for the troll?”.
  2. The trigger has a reply template. This one is tell %1, so %1 becomes “hagbard”. A trigger with no template has no Reply button, only Open.
  3. You tap Reply and type. Gboard opens inside the notification. The template is shown in front of what you type, so you know what will be sent.
  4. Send. The service sends tell hagbard sure, omw over the open connection, the same as if you had typed it in the app. The app doesn't open. The session shows [reply] tell hagbard sure, omw so you can see it later.

If the phone has a PIN or fingerprint lock, Android asks you to unlock before the reply is sent. That's the default because a reply is a real command to your character. You can turn it off per trigger. If the connection dropped in the meantime, the reply waits and is sent after the app reconnects. Several tells from the same person stack into one conversation notification, not a pile of separate ones.

Color & protocol

ANSI palette, tuned for black

Architecture

Following Android's recommended app architecture

This follows Google's guide to app architecture: data flows one way, the UI is driven by state, and each layer only talks to the one below it. The telnet and ANSI code is plain Kotlin with no Android dependencies, so it is unit tested on its own.

SessionService

Foreground service. It keeps the process alive and does very little else.

  • Observes SessionRepository to update the notification
  • Holds the Wi-Fi lock
  • Handles notification actions: reply, disconnect
  • No socket code of its own

A line from the server, start to finish

socket bytes→ MCCP inflate→ telnet: strip IAC, negotiate→ ANSI → styled spans→ TriggerEngine→ scrollback ring buffer→ LazyColumn

A command from you

text field→ # command? handle locally→ split on ;→ AliasExpander→ socket

Each stored rule has an optional world ID: empty means global. RuleResolver combines the global rules with the current world's rules into one list, and rebuilds it whenever either set changes, so edits take effect on the next line. Triggers match the plain text of a line (colors stripped), so a pattern you copy from the screen always matches. Scrollback keeps 5,000 lines by default. When you scroll up, auto-scroll pauses and a “12 new lines ↓” chip appears.

Two modules. mud holds the protocol and rules logic with no Android dependencies, so it is tested fast on the JVM. Everything Android lives in app, organized by package. The build plan has the full package layout.

Build order

Milestones

The full build order, package layout and technical decisions are in the Tether Build Plan. In short: skeleton, protocol, worlds, live session, staying connected, display and settings, rules engine, rules screens, notifications, polish.

Not in v1: Lua or other scripting, several connections at once, maps, GMCP gauges, on-screen buttons of any kind.

Before we build

Questions to confirm

  1. Is this for the Play Store, or just installed on your phone? Proposed: just your phone for now. Play reviews specialUse services and battery-optimization requests, which is extra paperwork.
  2. Plain telnet only, or TLS as well? Proposed: telnet in milestone 1, TLS in milestone 3.
  3. Is one connection at a time enough? Proposed: yes for v1. The data layer is built so more can be added later.
  4. TinTin++-style commands: #alias {k} {kill %1}, #action {%1 tells you: %2} {#notify}? Proposed: yes, with the braces optional for one-word arguments. Regex available in the editor.
  5. Command history without buttons: swipe up and down on the text field to scroll through past commands? Proposed: yes. It needs no extra buttons and doesn't touch Gboard.
  6. Use ; to separate several commands on one line? Proposed: yes, with \; to send a literal semicolon.
  7. When you type #alias, should it apply to this world only, with #galias for all worlds? Proposed: yes. Per-character rules are the more common case mid-session, and the Rules screen can copy or move it later.
  8. If a world alias and a global alias have the same name, does the world one win? Proposed: yes. Triggers don't override each other: matching global and world triggers both fire.
  9. Hide Android's status bar (clock, battery) in sessions to free one more line? Proposed: off by default, one switch in Settings. Swipe down from the top to see it briefly.
  10. Keep the name “Tether”?
